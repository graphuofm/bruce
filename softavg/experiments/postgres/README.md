# experiments/postgres — PostgreSQL before / after for `softavg`

**Timings here are smoke numbers on a shared machine** (`results.json` ->
`timing_status = "smoke, machine shared"`): other agents were compiling and
benchmarking on the same box. Use them to check that the harness works and
that the plans behave as expected, not to draw performance conclusions. The
main thread re-runs the timings serially on an idle machine.

Every number below is generated by `summarize.py` from `results.json`;
nothing in this file is typed by hand.

## What is compared (PROTOCOL "之前 / 之后")

Same server, same `imdb` table (IMDb corpus, all rows), same score
expression; only the aggregate spelling changes:

| plan | SQL |
|---|---|
| `naive` | `SUM(EXP(s/eps)*value) / SUM(EXP(s/eps))` |
| `shift` | per-facet `MAX(s)` in a CTE, `EXP((s-m)/eps)` |
| `clamp` | `shift` with `GREATEST((s-m)/eps, -700)` (PG raises on exp underflow) |
| `softavg` | bruce_pg 0.2.0 `softavg(value, s, eps)` (internal state over softagg-core) |
| `softavg_v012` | the 0.1.2 `float8[5]` state path, built from functions the same 0.2.0 `.so` still ships (state-representation A/B) |
| `topk_avg` | pgvector HNSW `ORDER BY emb <#> q LIMIT k`, then `AVG(value)` per facet; scored against the full-table softavg at every eps, plus facet coverage |
| `topk_softavg` | same top-k rows, then `softavg` |

Score `s`: `live` = `-(emb <#> q)` computed in the query by pgvector;
`precomp` = a float8 column holding the score of query j (isolates the
aggregation). eps grid `1e-4, 1e-3, 0.02, 0.1, 1, inf`; filter none and the
PROTOCOL predicate `filter_num >= 2000`; workers 0 and 8. Errors are recorded
verbatim (`error_message`, `sqlstate`). `max_rel_err` is against a numpy
float64 max-shifted reference computed from the scores the server holds or
computes. The query workload is the PROTOCOL sampler (`queries.json`, 200
queries); this smoke run uses the first three.

Also measured:

- **Sliding windows** (`window.py`): `softavg(...) OVER (ORDER BY id ROWS
  BETWEEN k PRECEDING AND CURRENT ROW)` through the new moving-aggregate form,
  against `softavg_fwd` (same internal state, no moving form, so PostgreSQL
  re-aggregates every frame) and the naive `SUM(EXP()) OVER w` spelling
  (PostgreSQL's float8 `sum` has no inverse; recorded from the catalog in
  `results.json`). Correctness against a numpy f64 per-frame reference;
  `punts` = how often `MINVFUNC` returned NULL because softagg-core's
  cancellation guard fired.
- **Incremental maintenance** (`maint_ivm/run.py`): `SELECT facet,
  softavg(value, s0, eps) GROUP BY facet` kept current under a stream of
  single-row INSERT / DELETE / UPDATE statements. Arms: bruce_pg
  `softavg_ivm_create` (per-facet `InvAcc` state table, statement triggers,
  inexact groups recomputed in the same statement), pg_ivm IMMV of the linear
  `SUM(EXP(s/eps)*v)` / `SUM(EXP(s/eps))` form, `REFRESH MATERIALIZED VIEW` of
  the softavg query at every checkpoint, and recompute-on-read. Per-op latency,
  groups recomputed, drift vs a fresh query at every checkpoint (in units of
  the value scale), read latency; plus a ROLLBACK check and a two-session
  concurrency check (both orders) of `softavg_ivm`.
- **Upgrade** (`upgrade_check.py`): `CREATE EXTENSION bruce_pg VERSION
  '0.1.2'` + views, `ALTER EXTENSION ... UPDATE TO '0.2.0'`, values and
  catalog compared with a fresh 0.2.0 install.

## What the smoke run shows (qualitative; numbers in the tables above)

- **Breakage before**: `naive` overflows and `shift` underflows (PostgreSQL
  raises on `exp` underflow) at the two sharp eps values, serial and
  parallel; `clamp` and `softavg` answer at every eps with errors at
  float64-rounding level against the numpy reference.
- **State representation (problem 1)**: the 0.2.0 internal state is faster
  than the 0.1.2 `float8[]` path and no slower than `naive` on precomputed
  scores; the parallel plan uses the new serial/deserial functions
  (`Partial HashAggregate` under `Gather Merge`). `shift`/`clamp` barely
  parallelise (the per-facet MAX subquery is re-run per worker).
- **Live score**: `naive` evaluates `-(emb <#> q)` twice per row, `softavg`
  once, so the live-score rows mix aggregation cost with score cost; the
  precomputed-score rows isolate the aggregation.
- **Top-k**: coverage below 1 at small k, and both `AVG` and `softavg` over
  the top-k rows disagree with the full-table answer except at sharp eps
  with large k.
- **Windows**: the moving aggregate stays flat in k while frame recompute
  (`softavg_fwd`, `naive_window`) grows with k. With softagg-core's running
  error bound every moving-aggregate cell is within the PROTOCOL's
  `|err| <= 1e-9 max|v|`; compared with the previous guard
  (`window_rel_core_v0.jsonl`) the error fell and the guard punts somewhat
  more often at eps <= 0.02.
- **Maintenance**: `softavg_ivm` keeps the view within rounding of a fresh
  query at every checkpoint and every eps, recomputing a handful of groups
  (mostly when an argmax row leaves at sharp eps), with reads that only scan
  the small state table. pg_ivm cannot create the linear IMMV at eps = 1e-3
  (overflow) and refuses a `softavg` IMMV outright; where it exists, its
  per-op cost is higher than `softavg_ivm`'s in this run. A REFRESHed MV is
  stale between refreshes; recompute-on-read pays a full scan on every read.
  ROLLBACK leaves the state bytes identical, and two sessions writing the
  same group serialize on its state row and end with the correct answer in
  both orders.
- **Upgrade**: 0.1.2 -> 0.2.0 keeps view/MV values bit-identical and the
  upgraded catalog equals a fresh install.
